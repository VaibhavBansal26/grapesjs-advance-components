grapesjs-advance-components

Accessible, themeable GrapesJS blocks, plus Stripe checkout, multi-page export and AI block generation that works with any model provider.

Open the playground Quick start

32 blocks

Hero, FAQ, pricing, forms, slider, header, footer and more, with no runtime dependencies.

AI, your provider

You supply the model call. No key in the package, output sanitized.

Stripe checkout

Hosted-page redirects only. Card data never touches your page.

Prompt to site

Forms that submit

Validation, honeypot, live status. Posts to your endpoint.

Multi-page

Page manager and a one-call export to a standalone static site (.zip).

Two packages

The project ships as two npm packages that work together. Pick by what you want to do:

PackageUse it toStart
grapesjs-advance-componentsEmbed an editor with 32 accessible blocks, forms that submit, Stripe checkout, page export and bring-your-own-model AI in your own app. Browser only.npm i grapesjs grapesjs-advance-components
promptsiteGenerate a finished multi-page site from one sentence, edit it visually, audit it for leaks, or run an HTTP API for n8n and CI. Node only.npx promptsite generate "…"

promptsite is built on the plugin. The plugin never depends on it, so if you only embed the editor you carry no CLI or server code.

Generate a whole site from a prompt

The promptsite command line tool writes a multi-page site from one sentence, lets a person polish it in the visual editor, and exports plain static files you can host anywhere. There is nothing to install first: npx fetches it (Node 18 or newer).

export ANTHROPIC_API_KEY=sk-ant-...        # your own key; read from the environment, never stored

npx promptsite generate "Family bakery in Leeds, sourdough and custom cakes, order online" \
  --template local-business --accent "#b45309" --form-endpoint https://api.example.com/contact \
  --out ./bakery

npx promptsite edit ./bakery        # visual editor on http://127.0.0.1:4173 (autosaves; Publish writes ./bakery/public)

No key yet? --provider mock writes placeholder copy so you can try the whole pipeline offline.

What you get

bakery/
  project.json     the editable GrapesJS project (open it with `promptsite edit`, load it in your own editor)
  promptsite.json         your settings (template, brand colour, form endpoint, payment link)
  public/          index.html, about.html, contact.html + .css + .js: static, no framework, CSP-friendly
TemplatePagesFor
landingHome, Pricing, ContactSaaS or product: hero, benefits, testimonials, FAQ, plans
local-businessHome, About, ContactShop, studio or service: hero, services, about, testimonials
shopHome, ContactProducts or plans with Stripe buttons, FAQ and a newsletter signup

How it works

  1. The model writes copy, not markup. It returns JSON (headline, features, FAQ, plans…) that is validated and bounded. An unusable reply is retried once with the problem explained.
  2. Templates build the pages from this package's own blocks (hero, features, FAQ, pricing, form). Every model string is escaped by the tool, so the output is safe by construction and fully editable afterwards.
  3. You review in the editor. promptsite edit opens the project with the ✨ button wired to the same model through the local server, so your key never reaches the browser.
  4. Export is deterministic. promptsite build re-renders project.json to public/, so CI can rebuild the site from the committed project.

The local editor is locked down

promptsite edit can write files and spend your API key, so it binds to 127.0.0.1 only, rejects any request whose Host or Origin is not itself (blocking DNS-rebinding and cross-site requests from other tabs), requires JSON bodies, and only publishes files named [a-z0-9-].html|css|js into public/. These rules are covered by tests.

What this is and is not. The copy is a draft: prices and testimonials are placeholders the tool tells you to replace, and it never invents facts you did not give it. The pipeline is tested end to end with the mock provider and a fake API server; output quality with a live model depends on the model and your brief. Pages have no images yet, and deployment is not included (public/ is plain files for any static host). The first run installs jsdom and grapesjs as dependencies, because the site is rendered in a headless editor.

What can you build with it?

This package is for teams that want users or staff to build web pages inside their own product. It extends GrapesJS, so your app embeds the editor and you decide where the pages are stored and published. Six scenarios:

1. Customer-built pages in a SaaS

Who: booking tools, course platforms, link-in-bio and community products.
How: embed the editor in your dashboard, save each customer's project JSON, publish the export on their subdomain.
Uses: blocks, theming, multi-page, export.

2. Agency site-delivery pipeline

Who: freelancers and agencies selling "your site in an hour".
How: intake form → promptsite generate drafts the pages → a person polishes them in promptsite edit → deploy public/.
Uses: the site generator, forms, Stripe links.

3. Internal campaign pages

Who: marketing teams that wait on developers for every landing page.
How: a private editor with your brand's blocks and colours; staff can't break the design system.
Uses: blocks, --aac-* theming, hide blocks you don't want.

4. Sell from a page

Who: creators and founders with a product and no checkout backend.
How: a pricing card whose button opens a Stripe Payment Link.
Uses: Pricing and Checkout blocks (see Stripe checkout).

5. Programmatic pages

Who: products that need one page per city, store or listing.
How: generate each project from data (and optionally AI copy), render on the server, publish static files.
Uses: headless render recipe below.

6. FAQ and help pages

Who: support teams that want an editable help centre without a CMS.
How: the accessible FAQ accordion, headings and links, exported as static pages.
Uses: FAQ block, multi-page.

Not a fit: database-backed content, logins, or server-rendered apps. The output is static HTML, CSS and a little JavaScript. Scenarios 2 and 5 are plausible and the pieces are tested, but they are not yet proven end to end with a real model or a live Stripe account.

Example: agency delivery pipeline

# 1. from the client's intake answers
npx promptsite generate "$BRIEF" --template local-business --name "$CLIENT" --accent "$BRAND" \
  --form-endpoint "https://api.youragency.com/leads/$CLIENT" --out "sites/$CLIENT"

# 2. a person reviews and edits
npx promptsite edit "sites/$CLIENT"

# 3. rebuild from the committed project in CI, then deploy the static files
npx promptsite build "sites/$CLIENT" && your-deploy-tool "sites/$CLIENT/public"

Integration guides

The plugin only needs a GrapesJS editor, so it works in any framework. The rules are the same everywhere: create the editor in the browser only, and destroy it when the component goes away.

React

GrapesJS also publishes an official wrapper, @grapesjs/react. The plain pattern below has no extra dependency.

import { useEffect, useRef } from 'react';
import grapesjs from 'grapesjs';
import 'grapesjs/dist/css/grapes.min.css';
import advanceComponents, { createFetchGenerator } from 'grapesjs-advance-components';

export function Builder({ project, onChange }) {
  const el = useRef(null);

  useEffect(() => {
    const editor = grapesjs.init({
      container: el.current,
      height: '100vh',
      storageManager: false,              // you own persistence, see "Saving and loading"
      projectData: project,
      plugins: [advanceComponents],
      pluginsOpts: { [advanceComponents]: { ai: { generate: createFetchGenerator('/api/ai') } } },
    });
    editor.on('update', () => onChange(editor.getProjectData()));   // debounce this in real apps
    return () => editor.destroy();       // also makes React StrictMode's double mount safe
  }, []);

  return <div ref={el} />;
}

Next.js

GrapesJS touches window and document, so it must not render on the server (otherwise: window is not defined). Mark the component as a client component and load it with SSR switched off:

// app/builder/page.jsx
'use client';
import dynamic from 'next/dynamic';
const Builder = dynamic(() => import('../../components/Builder'), { ssr: false });
export default function Page() { return <Builder />; }

Your two API routes keep secrets on the server. The AI route is the same idea as examples/ai-server.mjs. A Stripe Checkout Session route:

// app/api/checkout/route.js: creates a Checkout Session and returns its hosted-page URL
const PRICES = new Set(process.env.ALLOWED_PRICE_IDS.split(','));   // never trust a client-sent price blindly

export async function POST(req) {
  const { priceId, quantity = 1 } = await req.json();
  if (!PRICES.has(priceId)) return Response.json({ error: 'unknown price' }, { status: 400 });

  const body = new URLSearchParams({
    mode: 'payment',
    'line_items[0][price]': priceId,
    'line_items[0][quantity]': String(Math.min(Math.max(Number(quantity) || 1, 1), 10)),
    success_url: `${process.env.SITE_URL}/thanks`,
    cancel_url: `${process.env.SITE_URL}/pricing`,
  });
  const res = await fetch('https://api.stripe.com/v1/checkout/sessions', {
    method: 'POST',
    headers: { Authorization: `Bearer ${process.env.STRIPE_SECRET_KEY}`, 'Content-Type': 'application/x-www-form-urlencoded' },
    body,
  });
  const session = await res.json();
  if (!res.ok) return Response.json({ error: 'checkout failed' }, { status: 502 });
  return Response.json({ url: session.url });   // the button redirects here (checkout.stripe.com is allowlisted)
}
Use Stripe test mode keys while integrating, and fulfil orders from webhooks, not from /thanks.

Saving and loading

Pages, styles and assets live in the standard GrapesJS project data, so any storage manager persists them. Remote storage to your own API:

storageManager: {
  type: 'remote',
  autosave: true,
  stepsBeforeSave: 5,                         // batch saves instead of one request per edit
  options: { remote: {
    urlStore: `/api/projects/${id}`,
    urlLoad:  `/api/projects/${id}`,
    fetchOptions: (opts) => (opts.method === 'POST' ? { method: 'PUT' } : {}),
    onStore: (data) => ({ data }),            // body sent to your API
    onLoad: (result) => result.data,          // project JSON back into the editor
  } },
}

Server-side rendering of saved projects

A common question is how to turn stored project JSON into HTML on the server, without a browser or editor UI. GrapesJS has a headless mode, and the export helpers run in it. examples/render-site.mjs renders a project to a folder of static files. (For projects generated with promptsite, promptsite build <dir> does this for you.)

npm i grapesjs grapesjs-advance-components jsdom
node examples/render-site.mjs project.json ./out      # writes index.html, pricing.html, *.css, *.js

Node has no DOM, so the script gives it one with jsdom before importing GrapesJS. This was run end to end from a packed install in a clean directory.

Publishing under a strict Content-Security-Policy

By default each exported page carries an inline <style> and <script>. If your site forbids inline code, export external files instead:

exportSiteFiles(editor, { assets: 'external' });
// { 'index.html', 'index.css', 'index.js', 'pricing.html', … }, linked with <link> and <script src defer>

This covers published pages. It does not change how the editor itself runs; see the CSP note under Problems.

Publishing the files

The package produces files; it does not host them. exportSiteFiles() returns a plain { path: content } map you can zip (createZip), upload to object storage, commit to a repo, or hand to a static host's upload API.

What is built in

  • States: hover, active and visible keyboard focus on buttons, form fields and FAQ rows.
  • Responsive: the header and footer wrap, the slider and pricing card tighten below 640px.
  • Motion: transitions switch off under prefers-reduced-motion.
  • Variants: add the class aac-button--outline to a button for the outline style.
  • Typography is yours. Blocks inherit your page's font. They do not set a font family.

The stylesheet is also exported (import { baseCss } from 'grapesjs-advance-components') if you want to extend it, and injectStyles: false turns it off entirely.

Two GrapesJS behaviours shaped this stylesheet, and both are enforced by tests. Its CSS parser silently drops a shorthand such as background: var(…) or border-color: var(…), so custom properties only appear in longhand properties. And it keeps only the last rule for a selector, so each selector is declared exactly once. If you add your own rules through editor.Css, the same two rules apply.

Progress bar

A real component (aac-progress-bar, made with defineComponent) with percentage (0–100, clamped) and color traits. The bar uses your --aac-accent until you pick a colour. State lives in the inner element's style and aria-valuenow stays in sync, so exported HTML needs no script. Saved HTML is recognised again when loaded.

AI block generation

Describe what you want ("pricing FAQ for a project-management SaaS") and it lands on the canvas as editable components, inserted below the selection or replacing it. Undo works as usual. You provide the model call, so there is no vendor lock-in and no API key in the browser.

1. Through your backend

import advanceComponents, { createFetchGenerator } from 'grapesjs-advance-components';

pluginsOpts: {
  [advanceComponents]: {
    ai: { generate: createFetchGenerator('/api/ai') },

}

Stripe checkout

The Checkout and Pricing blocks add a button that sends the visitor to a Stripe-hosted page. Card details never touch your page or this package, and no secret key is ever involved.

ModeHow it works
linkRedirects to a Payment Link (https://buy.stripe.com/…). No backend needed.
sessionPOSTs { priceId, quantity } to your endpoint, which creates a Checkout Session with your secret key and returns { url }.
components: [
  { label: 'Buy', name: 'checkout', category: 'Commerce', componentType: 'checkout',
    checkoutElement: { mode: 'link', url: 'https://buy.stripe.com/xxxx', buttonText: 'Buy now' } },
]
payments: { allowedHosts: ['checkout.stripe.com', 'buy.stripe.com'] }   // default

Safety and hooks

  • Redirects only go to https hosts in allowedHosts; anything else is blocked and reported (https://buy.stripe.com.evil.com is rejected). Add your host if you use a custom Checkout domain.
  • The button is inert inside the editor canvas.
  • Its settings are data-mode, data-url, data-endpoint, data-price-id and data-quantity on the <button>, so a saved or generated page keeps them without any extra state. The allow-list is embedded in the script.
  • Cancelable events bubble from the button: aac:checkout (detail.url; call preventDefault() to take over the redirect or send analytics) and aac:checkout-error (detail.message).
  • While a session request is in flight the button has aria-busy="true"; errors show through data-error.
The package never validates payments. Fulfil orders from Stripe webhooks on your server, not from the success page.

Forms that submit

The Contact form and Newsletter blocks post to your endpoint, or to a form service such as Formspree or Netlify Forms. Set the endpoint in the trait panel, or in the plugin options:

components: [
  { label: 'Contact', name: 'form', category: 'Form', componentType: 'form',
    formAction: { endpoint: 'https://api.example.com/contact', encoding: 'json',
                  successMessage: 'Thanks, we will reply soon.', redirectUrl: '/thanks.html' } },
]
BehaviourDetail
ValidationUses the browser's built-in validation (required, type="email"); nothing is sent until the form is valid.
Sendingfetch POST of JSON (default) or form-encoded data (encoding: 'form', which form services expect). File uploads are not supported.
StatesAn aria-live status line shows sending, success and error. Values are kept when sending fails and cleared on success.
BotsA hidden honeypot field (_gotcha). If a bot fills it, the form looks successful and sends nothing. It is a first line of defence only.
No JavaScriptThe form still has method="post" and your action, so it falls back to a normal browser POST.
SafetyEndpoints must be https (or http on localhost). An empty, javascript: or plain-http endpoint is refused with a visible message.

Events

Cancelable and bubbling, on the form element of the published page:

form.addEventListener('aac:form-submit', (e) => {
  e.preventDefault();                       // take over sending (your own API client, analytics, CAPTCHA token…)
  myApi.send(e.detail.data);                // { name, email, message }
});
form.addEventListener('aac:form-success', (e) => track('lead', e.detail.data));
form.addEventListener('aac:form-error',   (e) => console.warn(e.detail.message));

A backend in a few lines

// Next.js: app/api/contact/route.js
export async function POST(req) {
  const { name, email, message } = await req.json();
  if (!name || !/^\S+@\S+\.\S+$/.test(email) || !message) return Response.json({ error: 'invalid' }, { status: 400 });
  await sendEmail({ to: process.env.INBOX, replyTo: email, subject: `Message from ${name}`, text: message });
  return Response.json({ ok: true });
}
Add server-side rate limiting and, for public sites, a CAPTCHA. A honeypot stops simple bots, not determined spam. If the form and the API are on different origins, the API must send CORS headers allowing your site.

Multi-page sites

GrapesJS has a native Pages API, and the plugin builds on it. A Pages button (📄) in the options panel opens a manager to add, rename, switch and delete pages and to download the whole site.

editor.runCommand('aac:pages');          // open the manager
editor.runCommand('aac:download-site');  // site.zip with one HTML file per page

Linking between pages

Set a link's href to page:<slug> (the slug of the page name, e.g. page:about-us). It is rewritten to about-us.html on export. The first page is always index.html.

Export from code

import { exportSite, exportSiteFiles, createZip } from 'grapesjs-advance-components';

const pages = exportSite(editor, { lang: 'en', siteName: 'Acme', description: 'What Acme does', head: '<link rel="icon" href="/f.ico">' });
// [{ id, name, file: 'index.html', html, css, js, document }, ...]   (js = component scripts, e.g. checkout)

const files = exportSiteFiles(editor);     // { 'index.html': '...', 'about.html': '...' }
const safe  = exportSiteFiles(editor, { assets: 'external', securityHeaders: true });   // + .css/.js and a strict-CSP _headers file
const zip = createZip(files);              // Uint8Array, no dependencies

Component scripts (such as the checkout button's) are included in every export, inline by default or as .js files with assets: 'external' (see strict CSP). Pass siteName and description to get proper <title> tags (About · Acme) and a meta description on every page. Page names are escaped in the title, and duplicate file names get a numeric suffix. Pages are stored in the normal GrapesJS project data, so any storage manager persists them.

Automation: n8n, CI and any workflow tool

Everything the CLI does is also available as a small HTTP API, so n8n, Zapier, Make or a cron job can generate, build and audit sites without a human at a terminal.

export ANTHROPIC_API_KEY=...                       # stays on this machine
export PROMPTSITE_API_TOKEN="$(openssl rand -hex 24)"     # 24+ characters, required
npx promptsite serve --root ./sites --port 8787           # http://127.0.0.1:8787
RequestDoes
GET /healthLiveness, no token needed.
POST /v1/generate{ slug, brief, template?, name?, accent?, theme?, formEndpoint?, paymentLink?, force? } writes sites/<slug>/ and returns pages, files and scanner notes.
POST /v1/build{ slug } re-renders project.json to public/.
POST /v1/audit{ slug } returns { passed, summary, findings }.
GET /v1/sitesLists generated sites.
GET /v1/sites/<slug>/bundle.zipThe public/ folder as a zip, ready for a deploy step.

Every call except /health needs Authorization: Bearer $PROMPTSITE_API_TOKEN.

n8n

examples/n8n/site-intake.workflow.json is an importable workflow: webhook → generate → audit → respond. The token lives in an n8n Header Auth credential, never in the workflow file, and the webhook has its own header credential. The README next to it has the five setup steps.

The workflow is written from n8n's documented node formats and verified for structure by a test (valid connections, no secrets), but it has not been imported into a running n8n by the author. Import it and run it once with test data before relying on it. A dedicated n8n community node is possible later; it would have to be its own package.

CI

# .github/workflows/site.yml
- run: npx promptsite build ./site                  # re-render from the committed project.json
- run: npx promptsite audit ./site --strict         # fails the build on a leak or unsafe markup
- run: your-deploy-tool ./site/public

promptsite audit exits non-zero when it finds a high-severity problem (or a medium one with --strict) and supports --json for scripts. It scans public/, project.json and promptsite.json, or any folder you point it at.

Build your own component

defineComponent turns a piece of HTML into a GrapesJS component with a block, settings in the trait panel, CSS and an optional runtime script. It is the same API the Progress bar, Quote, Hero and Checkout blocks are built with. The HTML is the source of truth: every setting lives in the markup, so it survives export, re-import and promptsite build with no extra work.

1. A static block

import { defineComponent } from 'grapesjs-advance-components';

export const testimonial = defineComponent({
  id: 'acme-testimonial',            // unique type id: prefix it
  label: 'Testimonial',
  category: 'Social proof',
  icon: '💬',                    // SVG markup, or a short text such as an emoji
  html: `<figure class="acme-testimonial acme-testimonial--round">
    <blockquote>Tell people what changed for you.</blockquote>
    <figcaption>Name, Role</figcaption>
  </figure>`,
  editable: ['blockquote', 'figcaption'],   // double-click to edit these
  css: `.acme-testimonial{margin:24px 0;padding:24px;border-left-width:4px;border-left-style:solid;border-left-color:var(--aac-accent,#4f46e5)}`,
});

grapesjs.init({
  plugins: [advanceComponents],
  pluginsOpts: { [advanceComponents]: { custom: [testimonial] } },
});

That registers the component type, a acme-testimonial-block block and the CSS. The CSS is only exported on pages that use the component. Use one root element; saved HTML is recognised again by the root's first class (change that with detect).

2. Settings (traits)

traits: {
  tone:    { type: 'select', options: ['light', 'dark'], default: 'light',
             bind: { class: { light: 'acme-testimonial--light', dark: 'acme-testimonial--dark' } } },
  rounded: { type: 'checkbox', default: true, bind: { classIf: 'acme-testimonial--round' } },
  accent:  { type: 'color', bind: { cssVar: '--aac-accent' } },
}

For class and classIf the markup decides the starting value: put the class in your html to start with it on.

Without a bind a trait is stored as a data-<name> attribute on the root (priceId becomes data-price-id). A trait can have several binds, for example the Progress bar writes its percentage to both a width and aria-valuenow.

BindWritesReadable by a page script
{ attr: 'aria-valuenow', on? }an attributeyes
{ text: '.name' }the text of the matching elementyes
{ class: { value: 'class-name' }, on? }one class per option; the others are removedyes
{ classIf: 'is-on', on? }a class when a checkbox is checkedyes
{ style: 'width', unit?: '%', on? }an inline style on the elementno
{ cssVar: '--x', on? }a custom property in the inline styleno

on is a selector relative to the root and defaults to the root itself. Trait types are text, number (min, max clamp the value written), select, checkbox and color. Set ui: false to keep a setting out of the panel.

Read and write a setting from code with testimonial.get(component, 'tone') and testimonial.set(component, 'tone', 'dark'). Both are typed by the trait names.

3. A script on the published page

defineComponent({
  id: 'acme-counter',
  label: 'Counter',
  html: '<button type="button" class="acme-counter" data-start="0">0</button>',
  traits: { start: { type: 'number', default: 0 } },
  consts: { max: 10 },                          // JSON values embedded in the script
  script({ el, props, consts, inEditor, emit }) {
    let n = props.start;                        // typed from the traits
    el.addEventListener('click', () => {
      if (inEditor) return;                     // true inside the editor canvas
      n = Math.min(n + 1, consts.max as number);
      el.textContent = String(n);
      emit('acme:count', { n });                // bubbling CustomEvent from el
    });
  },
});

The script is copied into the exported page as text, so it must be self-contained: no imports and no variables from outside the function. Anything it needs goes through props (read from the markup when the page loads) or consts. It does not run in the editor canvas unless you set runInEditor: true. props only holds settings a page can read back; a trait bound only to style or cssVar is left out, and the types reflect that.

5. Selectors

Selectors in bind.on, editable and repeat support a small subset, checked when you call defineComponent: a tag, .class, #id, [attr], [attr=value], combinations of those, descendant (space) and child (>). A selector that matches nothing in your HTML is an error with the component id in the message, so typos fail at startup rather than silently.

Things to know

  • One rule per selector. GrapesJS keeps only the last CSS rule for a selector, so defineComponent reports a selector declared twice in css.
  • No var() inside shorthands. GrapesJS drops shorthand properties such as background or border when they contain var(…). Use longhand (background-color, border-left-color). The same check runs on the built-in stylesheet.
  • Unique ids. Installing a different definition under an id that is already registered, or one that clashes with a GrapesJS type, throws instead of overwriting it. Installing the same definition twice is harmless.
  • Block overrides. The plugin's components option can still rename or hide the built-in blocks (visible: false); for your own, use block.

Security

The goal is that secrets cannot end up in generated sites, logs or browsers. No tool can promise zero leaks, so this is layered, fails closed, and is explicit about what it cannot cover.

What is enforced

LayerWhat it does
Keys stay in the environmentANTHROPIC_API_KEY and PROMPTSITE_API_TOKEN are read from env, never from flags, never written to disk, never sent to a browser. The editor's ✨ button calls the model through the local server.
Output scanner (fail closed)Before anything is written, generate, build, the editor's Save and Publish, and the API scan for Anthropic, OpenAI, Stripe secret, GitHub, AWS and Slack keys, private keys, credentials in URLs, secret-looking query parameters, javascript: URLs, inline handlers and plain-http forms. A high-severity finding stops the write (422 over the API) and is shown redacted. --allow <rule> is the explicit opt-out.
Log redactionErrors are stripped of key formats and of the exact values of the keys in use, even if an upstream error echoes one.
Strict CSPExports include a _headers file (Netlify, Cloudflare Pages): script-src 'self', style-src 'self', no unsafe-inline or unsafe-eval, connect-src limited to your form endpoint. Tested in a browser: the form and checkout still work, and an injected inline script, an inline handler, a third-party script and a request to an unlisted origin are all blocked.
Closed-by-default serverspromptsite edit and promptsite serve bind to loopback. serve requires a 24+ character bearer token (constant-time compare), throttles repeated failures, rejects browser requests, caps body size, runs one job at a time with an hourly limit, and confines each site to its own folder. edit rejects any foreign Host or Origin.
Untrusted model outputThe CLI escapes every model string and never inserts it as HTML. The editor's AI results go through an allowlist sanitizer. Checkout redirects are limited to approved hosts; form endpoints must be https.
npx promptsite audit ./site            # fail on high severity
npx promptsite audit ./site --strict   # also fail on medium
npx promptsite audit ./site --json     # for scripts

What cannot be promised

  • Everything in a static site is public. Form endpoints, Payment Links and publishable keys are visible to every visitor by design. The scanner warns about URLs that look like credentials, but it cannot know that an ordinary-looking URL is secret.
  • A webhook URL is a bearer capability. If a public form posts straight to an n8n webhook, anyone can trigger that workflow. Put your own server in between, and keep privileged workflows off public webhooks.
  • The scanner is a heuristic. It recognises common token formats, not every possible secret.
  • Your brief goes to the model provider. Do not put confidential information in prompts.
  • Do not expose promptsite serve to the internet without TLS and a firewall in front.

Report vulnerabilities privately through GitHub (Security → Report a vulnerability); see SECURITY.md.

Migrating from v1

  • grapesjs is now a peer dependency; install it yourself.
  • Block ids are unchanged. The heading entry now registers h1–h6 unless headingType is set.
  • Entries that never produced a block (countdown, imageFeature, tab, form, icon) were removed. checkout now exists for real.
  • FAQ, slider, progress bar, divider and form markup moved to aac-* classes. Pages saved with v1 keep their inline styles.
  • The browser build is dist/index.global.js.
